# Popili versions

## Registering versions

Popili's [version numbers](https://cocotec.io/popili/doc/stable/versioning.html#popili-version) and
[release notes](https://cocotec.io/popili/doc/stable/release_notes.html) explain its releases. Register every Popili
version you need; the first one is the default. In `MODULE.bazel`:

```starlark
coco = use_extension("@rules_coco//coco:extensions.bzl", "coco")
coco.toolchain(
    c = True,
    cc = True,
    versions = ["1.5.0", "1.5.1"],
)
```

or, in `WORKSPACE`:

```starlark
coco_repositories(
    c = True,
    cc = True,
    versions = ["1.5.0", "1.5.1"],
)
```

Besides explicit versions such as `"1.5.1"`, two aliases can be used when registering versions
(`coco.toolchain(versions = ...)` or `coco_repositories(versions = ...)`), in `popili_version` pins and in
`popili_versions` lists: `"stable"`, the newest stable release, and `"testing"`, the current pre-release (a beta or
release candidate). Each rules_coco release fixes what they resolve to (see
[`version_aliases.bzl`](../coco/private/version_aliases.bzl)), so upgrading rules_coco can move them. List explicit
versions to stay on a version. [`--@rules_coco//:version`](flags.md#version) takes explicit versions only.

To register every stable release your rules_coco version knows of (1.5.0 onwards, no betas or release candidates), load
`AVAILABLE_STABLE_VERSIONS` from `@rules_coco//coco:repositories.bzl`. It lists them newest first, so the newest is the
default:

```starlark
load("@rules_coco//coco:repositories.bzl", "AVAILABLE_STABLE_VERSIONS", "coco_repositories")

coco_repositories(
    c = True,
    cc = True,
    versions = AVAILABLE_STABLE_VERSIONS,
)
```

`MODULE.bazel` cannot load `.bzl` files, so in bzlmod list the versions manually in
[`coco.toolchain`](reference/extensions.md#coco.toolchain).

Registering versions is cheap: Popili and its runtimes are downloaded only for the versions targets actually use. Two
things to be aware of, though:

- When the first version is an alias such as `"stable"`, or the list is `AVAILABLE_STABLE_VERSIONS`, upgrading
  rules_coco moves the default, and with it every unpinned target. To keep generated code and verification results the
  same across upgrades, list an explicit version first, or pin targets with `popili_version`.
- `bazel sync` fetches every declared repository, so with `AVAILABLE_STABLE_VERSIONS` it downloads every stable release
  for every platform.

## Selecting the version for a whole build

Everything without a pin uses the default, or the version [`--@rules_coco//:version`](flags.md#version) selects, for
example `bazel build --@rules_coco//:version=1.5.1 //...`. The flag takes an explicit version or `local`. A pin wins
over the flag, unless [`--@rules_coco//:force_version`](#trying-a-version-everywhere) is set. To set the flag for the
whole repository, add it to `.bazelrc`:

```
build --@rules_coco//:version=1.5.1
```

## Pinning targets

Choose the version per target with `popili_version` on the rules that run Popili:
[`coco_generate`](reference/defs.md#coco_generate), [`coco_verify_test`](reference/defs.md#coco_verify_test),
[`coco_fmt_test`](reference/defs.md#coco_fmt_test) (its `<name>.format` binary formats with the same version),
[`coco_architecture_diagram`](reference/defs.md#coco_architecture_diagram),
[`coco_state_diagram`](reference/defs.md#coco_state_diagram) and
[`coco_counterexample_diagram`](reference/defs.md#coco_counterexample_diagram). A pin applies to that target and all its
dependencies, so the [`coco_package`](reference/defs.md#coco_package) it reads, and that package's `deps`, are analysed
with the same version.

The C and C++ library macros ([`coco_cc_library`](reference/cc.md#coco_cc_library),
[`coco_cc_test_library`](reference/cc.md#coco_cc_test_library), [`coco_c_library`](reference/c.md#coco_c_library) and
[`coco_c_test_library`](reference/c.md#coco_c_test_library)) take `popili_version` too. It selects the runtime the
library links. It also pins the `coco_generate` targets in `generated_package` or `generated_packages` that have no
`popili_version` of their own, but not the library's `srcs`, `deps` or `gmock`. A library only builds from code
generated by its own version. So pin it like its `coco_generate`, unless that is pinned to the version unpinned targets
get anyway; otherwise the build fails, saying what to pin. For code generated by several versions, use one library per
version. A `cc_binary` that links libraries of different versions links each version's runtime, so only do that when
those runtimes can be linked together.

```starlark
coco_package(
    name = "modern",
    srcs = ["modern/src/Example.coco"],
    package = "modern/Coco.toml",
)

coco_generate(
    name = "modern_cpp",
    language = "cpp",
    package = ":modern",
    popili_version = "1.5.1",
)

coco_cc_library(
    name = "modern_cc",
    generated_package = ":modern_cpp",
    popili_version = "1.5.1",
)

coco_verify_test(
    name = "modern_verify",
    package = ":modern",
    popili_version = "1.5.1",
)
```

## Trying a version everywhere

To try a version on the whole repository without editing BUILD files, add
[`--@rules_coco//:force_version`](flags.md#force_version). Every `popili_version` pin is then ignored, and
`--@rules_coco//:version` (or the default when it is unset) applies everywhere:

```bash
bazel test --@rules_coco//:force_version --@rules_coco//:version=1.5.1 //...
```

Under this flag the `popili_versions` checks below only warn.

## Restricting the versions of a package

A [`coco_package`](reference/defs.md#coco_package) can list the Popili versions it is compatible with:

```starlark
coco_package(
    name = "modern",
    srcs = ["modern/src/Example.coco"],
    package = "modern/Coco.toml",
    popili_versions = ["1.5.1"], # only popili 1.5.1 may be used with this package
)
```

A target such as [`coco_generate`](reference/defs.md#coco_generate) or
[`coco_verify_test`](reference/defs.md#coco_verify_test) that runs Popili on the package at a version not in the list
fails, saying which pin to set or which version to add to the list. Matching is exact after alias resolution. Add
`"local"` to the list for the local toolchain. Each package also checks the version it is built with against the lists
of its `deps`, whether or not it typechecks. Those deps check their own `deps` in turn, so every transitive dep's list
is checked. Under [`--@rules_coco//:force_version`](#trying-a-version-everywhere) these checks only warn.

The list also steers the version the package itself is built with, on its own (`bazel build //:modern`) or beneath a
consumer:

- When the list has the version the package would get anyway (the default, the flag or a consumer's pin), it keeps that
  version.
- Otherwise it uses the first listed version that is registered, so the order only matters then. `local` is never picked
  this way, only selected explicitly.
- When no listed version is registered, the package fails, saying which versions to register.
- Under `--@rules_coco//:force_version` it follows the forced version like everything else.

With a [bring-your-own toolchain](toolchains.md#bring-your-own-toolchain), the list must name that toolchain's version.

### Workspaces

A [`coco_workspace`](reference/defs.md#coco_workspace) takes
[`popili_versions`](reference/defs.md#coco_workspace-popili_versions) too:

- A member without `popili_versions` of its own inherits the workspace's list, also through nested workspaces'
  [`parent`](reference/defs.md#coco_workspace-parent), and is checked against it.
- An inherited list is only checked: it doesn't steer the version the member is built with. A member built on its own at
  a version outside the list fails with a message suggesting two fixes: select a listed version with
  `--@rules_coco//:version` (in `.bazelrc` for the whole repository), or write the list on the package.
- A member or nested workspace with a list of its own must include every version the workspace lists: it may support
  more, never fewer. To add a version, share the list through a `.bzl` constant:

```starlark
# popili_versions.bzl
WORKSPACE_POPILI_VERSIONS = ["1.5.0", "1.5.1"]

# BUILD
load(":popili_versions.bzl", "WORKSPACE_POPILI_VERSIONS")

coco_workspace(
    name = "workspace",
    popili_versions = WORKSPACE_POPILI_VERSIONS,
    workspace = "Coco.toml",
)

coco_package(
    name = "modern",
    srcs = ["modern/src/Example.coco"],
    package = "modern/Coco.toml",
    popili_versions = WORKSPACE_POPILI_VERSIONS + ["1.6.0"],
    workspace = ":workspace",
)
```

## Where pinned targets' outputs go

A pin equal to the version the build uses anyway (the flag, or the default when the flag is unset) changes nothing: the
target is built in the same configuration as unpinned targets. A target pinned to any other version is built in a
configuration of its own, so its outputs and test logs land under `bazel-out/<cpu>-fastbuild-ST-<hash>/` rather than in
`bazel-bin` and `bazel-testlogs`. In CI, collect test results through the Build Event Protocol
(`--build_event_json_file`) or from `bazel-out/*/testlogs/**/test.xml`.

See [`e2e/multi_version`](../e2e/multi_version) for a full example, in both `MODULE.bazel` and `WORKSPACE` form.
