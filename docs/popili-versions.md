# Popili versions

## Registering versions

Register every Popili version you need; the first one is the default. In `MODULE.bazel`:

```starlark
coco = use_extension("@rules_coco//coco:extensions.bzl", "coco")
coco.toolchain(
    c = True,
    cc = True,
    versions = ["1.5.0", "1.5.1"],
)
```

or, in `WORKSPACE`:

```starlark
coco_repositories(
    c = True,
    cc = True,
    versions = ["1.5.0", "1.5.1"],
)
```

Besides explicit versions such as `"1.5.1"`, two aliases can be used when registering versions
(`coco.toolchain(versions = ...)` or `coco_repositories(versions = ...)`), in `popili_version` pins and in
`popili_versions` lists: `"stable"`, the newest stable release, and `"testing"`, the current pre-release (a beta or
release candidate). Each rules_coco release fixes what they resolve to (see
[`version_aliases.bzl`](../coco/private/version_aliases.bzl)), so upgrading rules_coco can move them. List explicit
versions to stay on a version. `--@rules_coco//:version` takes explicit versions only.

To register every stable release your rules_coco version knows of (1.5.0 onwards, no betas or
release candidates), load `AVAILABLE_STABLE_VERSIONS` from `@rules_coco//coco:repositories.bzl`.
It lists them newest first, so the newest is the default:

```starlark
load("@rules_coco//coco:repositories.bzl", "AVAILABLE_STABLE_VERSIONS", "coco_repositories")

coco_repositories(
    c = True,
    cc = True,
    versions = AVAILABLE_STABLE_VERSIONS,
)
```

`MODULE.bazel` cannot load `.bzl` files, so in bzlmod list the versions manually in `coco.toolchain`.

Registering versions is cheap: Popili and its runtimes are downloaded only for the versions
targets actually use. Two things to be aware of, though. The default is the newest version your
rules_coco release knows of, so upgrading rules_coco moves unpinned targets to a new Popili. List
explicit versions, or pin targets with `popili_version` (see below), if you need generated code
and verification results to stay the same across upgrades. And `bazel sync` fetches every
declared repository, so with this list it downloads every stable release for every platform.

## Pinning targets

Choose the version per target with `popili_version` on the rules that run Popili:
`coco_generate`, `coco_verify_test`, `coco_fmt_test` (its `<name>.format` binary formats with the
same version), `coco_architecture_diagram`, `coco_state_diagram` and `coco_counterexample_diagram`.
A pin applies to that target and everything beneath it, so the `coco_package` it reads is analysed
with the same version. Aliases such as `"stable"` are allowed.

`coco_cc_library`, `coco_cc_test_library`, `coco_c_library` and `coco_c_test_library` take
`popili_version` too. On a `coco_cc_library` it selects which version's runtime the library links,
and it also applies to the unpinned `coco_generate` targets the library builds from. The library's
own `srcs`, `deps` and `gmock` are not affected.

A `coco_cc_library` only builds from code generated by the same version. So if you pin a
`coco_generate`, pin the `coco_cc_library` that uses it to the same version; otherwise the build
fails with a message saying what to pin. You can skip this when the `coco_generate` is pinned to
the version unpinned targets get anyway: the default, or the value of `--@rules_coco//:version`.

All the `coco_generate` targets one `coco_cc_library` builds from must use the same version. For
code generated by several versions, use one `coco_cc_library` per version. A `cc_binary` that
links `coco_cc_library` targets of different versions links the runtime of each version, so only
do that when those runtimes can be linked together.

```starlark
coco_package(
    name = "modern",
    srcs = ["modern/src/Example.coco"],
    package = "modern/Coco.toml",
)

coco_generate(
    name = "modern_cpp",
    language = "cpp",
    package = ":modern",
    popili_version = "1.5.1",
)

coco_cc_library(
    name = "modern_cc",
    generated_package = ":modern_cpp",
    popili_version = "1.5.1",
)

coco_verify_test(
    name = "modern_verify",
    package = ":modern",
    popili_version = "1.5.1",
)
```

## Restricting the versions of a package

A `coco_package` can list the popili versions it is compatible with:

```starlark
coco_package(
    name = "modern",
    srcs = ["modern/src/Example.coco"],
    package = "modern/Coco.toml",
    popili_versions = ["1.5.1"], # only popili 1.5.1 may be used with this package
)
```

A target that runs another version on the package fails, saying which pin to set or which version
to add to the list. Matching is exact after alias resolution: `"stable"` gives the most recent
stable version that your rules_coco version is aware of. Add `"local"` to the list for the local
toolchain. A package checks the lists of its `deps` itself, whether or not it typechecks, and they
check theirs, so the list of every transitive dep is checked too. Under
`--@rules_coco//:force_version` (see below) the check only warns.

The list also steers the package's own build (`bazel build //:modern`, or beneath a consumer): it
keeps the version it would get (the default, the flag, or a consumer's pin) when its list has it,
and otherwise is analysed and typechecked with the first listed release that is registered, so
order only matters then; `local` is never picked, only selected explicitly. A consumer pinned to the
version the standalone build uses shares the package with it, so it is typechecked once. When no
listed release is registered, the package fails saying which versions to register. A
bring-your-own toolchain serves every target, so the list must name its version, and the flag and
pins must still name that version or be left out. Under `--@rules_coco//:force_version` the package
follows the forced version like everything else.

### Workspaces

A `coco_workspace` claims versions for all of its members with the same attribute. A member
without `popili_versions` of its own inherits the workspace's list, through nested workspaces'
`parent` as well, and is checked against it; only a list written on the package itself steers the
version the package is built with, though, since a transition cannot read another target. A member
built on its own at a version outside an inherited list fails, naming the fix: select a listed
version with `--@rules_coco//:version`, in `.bazelrc` for the whole repository, or write the list
on the package. A member or nested workspace with a list of its own must include every version
the workspace lists: it may support more, never fewer. To add a version, share the list through
a `.bzl` constant:

```starlark
# popili_versions.bzl
WORKSPACE_POPILI_VERSIONS = ["1.5.0", "1.5.1"]

# BUILD
load(":popili_versions.bzl", "WORKSPACE_POPILI_VERSIONS")

coco_workspace(
    name = "workspace",
    popili_versions = WORKSPACE_POPILI_VERSIONS,
    workspace = "Coco.toml",
)

coco_package(
    name = "modern",
    srcs = ["modern/src/Example.coco"],
    package = "modern/Coco.toml",
    popili_versions = WORKSPACE_POPILI_VERSIONS + ["1.6.0"],
    workspace = ":workspace",
)
```

## Selecting the version for a whole build

Everything without a pin uses the default, or the version `--@rules_coco//:version` selects, for
example `bazel build --@rules_coco//:version=1.5.1 //...`. The flag takes a concrete version (or
`local`); aliases such as `stable` are for pins only. A pin wins over the flag, unless
`--@rules_coco//:force_version` is set (see below).

A pin equal to the version the build uses anyway (the flag, or the default when the flag is unset)
costs nothing. A target pinned to any other version is built in a configuration of its own, so its
outputs and test logs land under `bazel-out/<cpu>-fastbuild-ST-<hash>/` rather than in `bazel-bin`
and `bazel-testlogs`. In CI, collect test results through the Build Event Protocol
(`--build_event_json_file`) or from `bazel-out/*/testlogs/**/test.xml`.

To try a version on the whole repository without editing BUILD files, add
`--@rules_coco//:force_version`: every `popili_version` pin is ignored, and
`--@rules_coco//:version` (or the default when it is unset) applies everywhere, for example
`bazel test --@rules_coco//:force_version --@rules_coco//:version=1.5.1 //...`.

See [`e2e/multi_version`](../e2e/multi_version) for a full example, in both `MODULE.bazel` and `WORKSPACE` form.

## Custom rules

rules_coco has no public API for rules of your own that run popili. A hand-written rule that
declares `@rules_coco//coco:toolchain_type` gets no `popili_version`, is not reached by
`--@rules_coco//:force_version` when it transitions the version flag itself, and the fields of the
toolchain it resolves are not a stable interface. `CocoPackageInfo` is public for rules that only
read a package's files, and `CocoCcGeneratedInfo` and `CocoCSharpGeneratedInfo` for rules that
consume the code a `coco_generate` target produced.
